# Domain model

Status: frozen for the v0.1 sprint. Changing a field, an enumeration or a
rule means changing this file, the ORM model, the Pydantic schema, the
migration and the tests together.

## Relationships

```text
Workspace 1 ── N Project
Workspace 1 ── N Supplier
Workspace 1 ── N Equipment
Workspace 1 ── N PurchaseOrder
Workspace 1 ── N IngestionBatch

Project  1 ── N Equipment
Project  1 ── N PurchaseOrder
Supplier 1 ── N PurchaseOrder

PurchaseOrder 1 ── N PurchaseOrderItem N ── 1 Equipment
PurchaseOrder 1 ── N Milestone 1 ── N MilestonePlanVersion
PurchaseOrder 1 ── N SupplierCommitmentVersion

IngestionBatch 1 ── N IngestionRow ── 0..1 canonical record (type + id)
```

- Equipment can exist without a purchase order. A procurement gap must be
  representable, so equipment has no supplier and no purchase-order column.
  The supplier of a piece of equipment is the supplier of the purchase order
  whose line item names it.
- A purchase order belongs to exactly one project and one supplier.
- A purchase order has any number of line items, including none: a header
  imported before its lines is a valid intermediate state and is reported by
  data quality.
- The same equipment may appear in several purchase orders (split
  procurement), but only once per purchase order.

## Conventions

| Topic | Rule |
|---|---|
| Identifiers | UUID, generated by the service (`uuid4`), with a database default as a backstop |
| Timestamps | `timestamptz`, UTC, taken from the service clock (`app.core.clock`) |
| Dates | PostgreSQL `DATE`; `YYYY-MM-DD` at every boundary |
| Money and quantity | `NUMERIC` in the database, `Decimal` in Python, a string in JSON. Never float. A value with more digits than the column holds is refused, never rounded |
| Whole numbers | PostgreSQL `INTEGER`: at most 2,147,483,647. A larger `sequence_no` or `offset` is refused at the boundary, never truncated. In JSON a whole number is a JSON number: `"1"`, `1.0` and `true` are refused |
| Text | Trimmed before it is stored. The NUL character is refused, because PostgreSQL text cannot hold it |
| Digits | In whole numbers and decimals a decimal digit of any script is the digit it is: `१२३.४५` is stored as `123.45`. Dates take the digits 0 to 9 only, because a date written in another script may be of another calendar and the calendar is never guessed |
| Enumerations | Stored as text with a `CHECK` constraint listing the allowed values |
| Natural keys | Unique within a workspace; immutable after creation; compared exactly as stored (trimmed, case-sensitive) |
| Deletion | No procurement fact is deleted. No delete operation exists |
| Table names | `workspaces`, `projects`, `suppliers`, `equipment`, `purchase_orders`, `purchase_order_items`, `milestones`, `milestone_plan_versions`, `supplier_commitment_versions`, `ingestion_batches`, `ingestion_rows` |

### Milestone

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `workspace_id` | UUID | Same as the purchase order |
| `purchase_order_id` | UUID | Required |
| `milestone_type` | enum | `PO_ACKNOWLEDGEMENT`, `DRAWING_SUBMISSION`, `DRAWING_APPROVAL`, `MANUFACTURING_START`, `FACTORY_ACCEPTANCE_TEST`, `DISPATCH`, `DELIVERY`, `INSTALLATION` |
| `sequence_no` | integer | Positive; allows the same type more than once |
| `actual_date` | date | Empty until completion is recorded |
| `status` | enum | `PENDING`, `COMPLETED`, `CANCELLED` |
| `created_at`, `updated_at` | timestamptz | |

Identity: `(purchase_order_id, milestone_type, sequence_no)`.

Planned and actual are separate facts. The planned date lives only in
`MilestonePlanVersion`. An actual date is recorded only on a `COMPLETED`
milestone. A milestone may be `COMPLETED` without an actual date when the
source says "completed" and gives no date: the date is not invented, and data
quality reports it as not recorded.

### SupplierCommitmentVersion (append-only)

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `workspace_id` | UUID | Same as the purchase order |
| `purchase_order_id` | UUID | Required |
| `version_no` | integer | Positive; unique per purchase order |
| `committed_delivery_date` | date | Required |
| `source_reference` | text(200) | Optional. The supplier's own reference for the commitment (letter or message number). An addition to the playbook table, for the "Source Reference" column of the commitments file |
| `source_ingestion_row_id` | UUID | FK → ingestion_rows, if any |
| `recorded_at` | timestamptz | |
| `recorded_by` | text(120) | Source label or actor |

**Version semantics, both tables.** A changed date is a new row with
`version_no = latest + 1`; no existing row is ever updated or deleted. The
current value is the row with the greatest `version_no`, never "the first row
a query returns". Submitting the date that is already current creates nothing.
Version numbers are allocated while the parent row (purchase order or
milestone) is locked, and `(parent, version_no)` is unique, so two writers
cannot produce the same number. Since migration 0002 PostgreSQL itself
enforces the rule too: `BEFORE UPDATE OR DELETE` and `BEFORE TRUNCATE`
triggers on both tables refuse a rewrite in any session that has not declared
itself maintenance with `SET LOCAL nexus.allow_history_rewrite = 'on'`. No
route and no service operation sets it; the test-suite cleanup and the
confirmed development reset of the demo seed do.

### IngestionBatch

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `workspace_id` | UUID | FK → workspaces |
| `entity_type` | enum | `project`, `supplier`, `equipment`, `purchase_order`, `purchase_order_item`, `milestone`, `supplier_commitment` |
| `original_filename` | text(255) | Display only; never used as a path. Stored as the last path segment, without characters that cannot be printed, cut to 255 characters; `upload` when nothing is left |
| `file_sha256` | char(64) | Lowercase hex SHA-256 of the uploaded bytes |
| `source_format` | enum | `CSV`, `XLSX` |
| `file_size_bytes` | integer | Positive |
| `sheet_name` | text(160) | XLSX only |
| `file_warnings` | JSONB | Findings about the file as a whole, such as skipped blank rows (addition) |
| `status` | enum | `UPLOADED`, `PREVIEWED`, `COMMITTING`, `COMMITTED`, `FAILED` |
| `total_rows`, `valid_rows`, `invalid_rows` | integer | Preview counters; not negative |
| `committed_rows`, `skipped_rows`, `failed_rows` | integer | Commit counters (addition); not negative |
| `commit_summary` | JSONB | The recorded commit result, returned unchanged when a commit is replayed (addition) |
| `created_at` | timestamptz | |
| `committed_at` | timestamptz | Set when the batch is committed |
| `failure_code` | text(64) | Set when the batch failed |

Uniqueness: `(workspace_id, entity_type, file_sha256)` among batches that are
not `FAILED`. Uploading the same bytes again for the same entity type
resolves to the existing batch. A `FAILED` batch wrote nothing canonical and
is left out of the rule on purpose: after a failure caused by the database
state or by an outage, the same file can be previewed again as a new batch.

The rule also holds when the same new file arrives several times at once.
The unique index lets one request create the batch; each of the others waits
for it, then finds that batch and answers with it. Every caller receives the
same batch id, and one batch exists.

### IngestionRow

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `batch_id` | UUID | FK → ingestion_batches |
| `row_number` | integer | Physical row number in the source file; unique per batch |
| `raw_data` | JSONB | The source values under their original headers, unchanged |
| `normalized_data` | JSONB | The canonical values derived from them: dates as `YYYY-MM-DD`, decimals as strings |
| `validation_errors` | JSONB | List of structured errors; empty when there are none |
| `warnings` | JSONB | List of structured non-blocking warnings |
| `status` | enum | `VALID`, `INVALID`, `COMMITTED`, `SKIPPED`, `FAILED` |
| `planned_action` | text(16) | What a commit would do, assessed at preview: `CREATE`, `UPDATE`, `NO_CHANGE` (addition) |
| `outcome` | text(40) | What the commit did: `CREATED`, `UPDATED`, `UNCHANGED`, `DUPLICATE_ROW`, `ROLLED_BACK`, `REJECTED` (addition) |
| `canonical_entity_type` | text(40) | Kind of the canonical record the row resulted in |
| `canonical_entity_id` | UUID | Its id |
| `created_at` | timestamptz | |

`canonical_entity_type` is one of `project`, `supplier`, `equipment`,
`purchase_order`, `purchase_order_item`, `milestone`,
`supplier_commitment_version`. The pair cannot be a foreign key, because it
points at seven tables. The ingestion service sets it only to a record it has
just created or resolved inside the same workspace and transaction. The row
and its batch are never deleted.

## Invariants and where they are enforced

| # | Invariant | Database | Service |
|---|---|---|---|
| 1 | Every business record has a workspace | `workspace_id NOT NULL` + FK | — |
| 2 | Every read and write is workspace-scoped | — | Every repository query filters on `workspace_id` |
| 3 | Related records share one workspace | Composite FKs `(workspace_id, parent_id)` on equipment, purchase orders, line items, milestones, commitments | Checked before writing |
| 4 | A purchase order and its line items and their equipment share one project | Composite FKs `(workspace_id, project_id, purchase_order_id)` and `(workspace_id, project_id, equipment_id)` | `CROSS_PROJECT_REFERENCE` |
| 5 | Equipment may exist without a purchase order | No such column | — |
| 6 | Quantity is positive; money is not negative | `CHECK` | `MUST_BE_POSITIVE`, `MUST_BE_NON_NEGATIVE` |
| 7 | Money and quantity are exact | `NUMERIC` | `Decimal`, strings in JSON |
| 8 | Plans and commitments are append-only | Unique `(parent, version_no)`; triggers refuse `UPDATE`, `DELETE` and `TRUNCATE` (migration 0002) | No update or delete operation exists |
| 9 | Natural keys are unique per workspace | Unique constraints | `DUPLICATE_NATURAL_KEY` |
| 10 | Nothing is hard-deleted | FKs without cascade | No delete operation exists |
| 11 | Unknown source columns are kept | `raw_data` | `UNKNOWN_SOURCE_COLUMN` warning |
| 12 | World State comes from persisted records | — | Read-only snapshot transaction |
| 13 | A batch is committed at most once | Row lock on the batch | Replay returns the recorded result |
| 14 | A failed commit leaves no canonical record | One transaction | Rollback, then a separate failure record |
| 15 | Dates are date-only | `DATE` | ISO `YYYY-MM-DD` only |
| 16 | An actual date belongs to a completed milestone | `CHECK` | `INCONSISTENT_MILESTONE_STATE` |
| 17 | One file, one batch per entity type | Partial unique index on `(workspace_id, entity_type, file_sha256)` | A request that loses the race answers with the batch that won |
| 18 | Two writers never allocate the same version number | Unique `(parent, version_no)` | The parent row is locked before the latest version is read |
| 19 | A value the database cannot hold never reaches it | Column types | Refused at the boundary with a field error; if one arrives all the same, the transaction is rolled back and the answer is 422, not 500 |

## Writers at the same time

| Situation | What happens |
|---|---|
| Two commits of one batch | The second waits on the batch row, then returns the recorded result with `replayed: true`. The batch takes effect once |
| Two imports, or an import and an API call, that touch the same purchase order or milestone | The second waits until the first transaction ends, then reads the latest version. A date that became current in the meantime creates no second version |
| The same new file uploaded several times at once | One batch; every caller receives it |
| Two files that create the same new record at once | One commits. The other meets the unique key: 409 `COMMIT_CONFLICT`, its batch is `FAILED`, nothing of it is written, and the file can be uploaded again |
| A deadlock | PostgreSQL ends one transaction. Nothing of it is written and the answer is 409 `CONFLICT`. A commit ended this way leaves its batch `PREVIEWED`, so the same request can be sent again |

An import takes its row locks in one fixed order: projects, suppliers,
equipment, purchase orders, then line items or milestones. Within one kind
the rows are locked in the order of the columns of the natural key (the
code or number; for a line item and a milestone, the purchase order first).

## Field ownership for imports

An import resolves a record by its natural key. It creates the record when
none exists; otherwise it may change only the fields listed as source-owned.
There is no "last row wins" over a whole record.

| Entity | Identity (never changed by an import) | Source-owned fields |
|---|---|---|
| Project | `code` | name, location, status, target completion date |
| Supplier | `supplier_code` | name, country, city, status |
| Equipment | `equipment_code`, project | name, category, specification, required-on-site date, criticality, procurement status |
| Purchase order | `po_number`, project, supplier | issue date, currency, total value, status |
| Line item | purchase order + equipment | quantity, unit price |
| Milestone | purchase order + type + sequence | actual date, status; the planned date only as a new plan version |
| Commitment | purchase order | nothing; a different date is a new version |

Three rules complete the policy:

1. **A blank cell means "not supplied".** It never clears a stored value and
   never replaces it with a default. Clearing a value is an explicit API
   update.
2. **An identity mismatch is an error, not an update.** A row that names an
   existing purchase order with a different project or supplier, or existing
   equipment with a different project, is rejected with
   `IMMUTABLE_FIELD_CONFLICT`.
3. **Duplicates inside one file.** Rows with the same natural key and the
   same values: the first is applied, the others are skipped as
   `DUPLICATE_ROW` and linked to the same record. Rows with the same natural
   key and different values: all of them are rejected with
   `DUPLICATE_NATURAL_KEY`. Row order never decides.

## Not in this model

Days late, schedule impact, supplier performance, delay probability, root
cause, recovery options, recommended substitution. They are derived later, by
a separate layer, from the facts above.
